Schema changes · Gabriel for Denver

Guides and Planks

Two new content collections, one new folder each, zero edits to anything already deployed. Both exist so the campaign can write the new platform months before it is switched on.

Grounded against main @ 07970fe — 13 Sept 2026  ·  plan.html  ·  design.html

01

Current schema, the slice that matters

Four collections live in src/content.config.ts: pages, issues, events, posts. Only issues is relevant, and only as the thing the new collections are deliberately not modifying.

src/content.config.ts — existing, unchanged by this proposal 
const issues = defineCollection({
  loader: glob({ pattern: '**/*.yml', base: './src/content/issues' }),
  schema: () => z.object({
    title, title_es, summary, summary_es, intro, intro_es,   // all z.string(), all required
    slug: z.string(), lucideIcon: z.string(), order: z.number(),
    subIssues: z.array(z.object({
      title, title_es, summary, summary_es,
      problemsAndSolutions: z.array(z.object({
        problem, problem_es, solution, solution_es,
      })),
    })).optional(),
  }),
})

Three properties of that shape carry over to the new collections, because they are the repo's conventions and not accidents:

  • YAML files with markdown inside string fields, parsed at render time with marked.parse() and injected via set:html. Not MDX, not frontmatter-plus-body.
  • Spanish as an _es twin on every translatable field. There is no dictionary and no i18n routing helper — one file holds both languages, and the Spanish pages under src/pages/es/ are hand-authored.
  • slug is an explicit field, not derived from the filename, and order is an explicit number, not a date.

Two properties deliberately do not carry over. The _es fields here are all required by Zod, which means an entry cannot be saved until it is fully translated — workable for six issues written in one sitting, hostile to writing eighteen planks over eight weeks. The new collections move that gate: _es is optional in the schema so a draft can be saved in English, and completeness is enforced at publish time instead, in the build. Drafting stays fluid; the two live sites never diverge. And the nesting goes two levels deep (subIssues[].problemsAndSolutions[]), which in Sveltia means a list widget inside a list widget: the single most-complained-about editing surface on the site today, and the reason the content is hard to add to.

The CMS is half the schema. public/admin/config.yml (Sveltia, GitHub backend, committing straight to main) mirrors every collection field for field. A Zod change without the matching CMS change produces content nobody can edit; a CMS change without the Zod change produces a saved entry that breaks the production build. They ship together, always.

02

New collection: guides

One file per issue area, at src/content/guides/<slug>.yml. Holds everything that is true of the whole guide and nothing that is true of a single promise.

Why a new collection rather than fields on issues

Every field above except title, slug, lucideIcon and order is new. Adding them to issues would mean editing the six YAML files that render the live site today, and would mean the CMS form for “Issues” growing fields that do nothing on the pages actually deployed — which is the specific failure the brief rules out. A guide also outlives the thing it replaces: it carries no summary, no intro, and no subIssues, so it is not a superset of an issue and could not be modelled as one without leaving four dead fields behind forever.

New collection: planks

One file per promise, at src/content/planks/<slug>.yml. This is the unit the whole design is built on: one plank is one band, one anchor, one sheet, one CMS entry, one draft flag.

Sources live on the plank, not the guide

The original sketch put a numbered sources list at issue level and had commitments cite it by id. That needs id bookkeeping across a file, breaks silently when an id is deleted, and — the real problem — assumes the reader is looking at the whole page. In this design the band is the shareable unit: someone screenshots one band, or lands on one plank's anchor. A footnote that lives two thousand pixels away from the claim it supports may as well not exist. Inline { label, url } objects per plank cost a little duplication when two planks cite the same study, and remove a whole class of dangling-reference bug.

The hero is resolved, not validated

A plank can carry a statValue, a pullQuote, or neither. Rather than a Zod .refine() enforcing exactly one, a pure function picks in priority order and the schema accepts all three shapes:

src/lib/platform.ts 
export type PlankHero =
  | { kind: 'stat'; value: string; caption: string }
  | { kind: 'quote'; quote: string }
  | { kind: 'statement'; text: string }

// Deliberately total: every plank resolves to some hero. A Sveltia save
// commits straight to main, so a schema that can reject an editor's entry
// is a schema that can take the whole campaign site's build down.
export function resolveHero(plank: Plank, lang: Lang): PlankHero

Falling back to the commitment itself as the hero is not a degraded state — a band whose enormous type is the promise is a perfectly good band, and it is the honest render for a plank that has no number behind it yet.

04

The join, and why it isn't a reference()

Astro's reference('guides') resolves against a collection entry's id, which for the glob loader is the filename minus its extension. This repo's convention is an explicit slug field that is only conventionally equal to the filename. Binding the join to reference() quietly makes those two things the same thing forever, and produces an Astro-internal error message when they diverge.

So plank.guide is a plain z.string(), and the join is done explicitly against guide.data.slug in one place, with an assertion that names the problem in the campaign's own vocabulary:

export function assertGuideRefs(guides: Guide[], planks: Plank[]): void {
  const known = new Set(guides.map(g => g.data.slug))
  const orphans = planks.filter(p => !known.has(p.data.guide))
  if (orphans.length === 0) return
  throw new Error(
    `Plank(s) point at a guide that doesn't exist: ` +
    orphans.map(p => `${p.id} -> "${p.data.guide}"`).join(', ') +
    `. Known guides: ${[...known].join(', ')}`,
  )
}

The CMS still gives the editor a dropdown rather than a free-text box — Sveltia's relation widget, configured to search the guides collection and write its slug. That the widget writes the value we expect is the one mechanical unknown in this proposal; it is the subject of Spike S1 in the plan.

Constraints, enforced in src/lib/platform.ts

  • Every plank points at a real guide — build fails loudly, as above.
  • Every related entry points at a real guide — same treatment.
  • Slugs are unique within their collection — two guides claiming housing-crisis would silently give one of them an unreachable route.
  • A published plank cannot sit under a draft guide — not an error, just filtered: the guide's status wins, so nothing leaks by way of a plank.
  • A published entry has every _es twin filled — build fails, naming the entry and the missing fields. This is the gate that lets _es be optional in Zod without the Spanish site quietly falling behind the English one. Draft entries are exempt, which is the whole point.

There are no database indices here. These are flat YAML files read at build time; eighteen to forty planks is a linear scan measured in microseconds, and any lookup structure would be ceremony.

06

Migration

Backward compatibility

Total, because nothing is modified. content.config.ts gains two entries in its collections export; the four existing ones are untouched, as are all six src/content/issues/*.yml files, /issues, /es/issues, and the Issues block in the CMS. The new collections are inert until a route reads them — the first PR ships schema, CMS config and helpers, and renders nothing at all.

There is no rolling-deploy concern to sequence around: this is a prerendered Astro site on Netlify, so every deploy is an atomic swap of a static bundle.

Backfill

By hand, and only once. housing-crisis is migrated as the reference entry — one guide and three planks — so there is a worked example for the other five to be written against. The remaining content is authored fresh in the CMS, not converted, and that is a deliberate choice rather than laziness: the old shape does not decompose into the new one. A wall of problem prose contains no commitment, no why line, no authority, and no sources; any script claiming to extract them would be inventing them. What the old files genuinely provide is the detail prose, which is copied across essentially verbatim.

This is why locking the schema comes before writing the content. Material written in the current shape has to be taken apart by hand afterwards — that is the expensive path, and it gets more expensive with every issue written.

Rollback

Delete the two collections from content.config.ts, the two blocks from public/admin/config.yml, and the route files. The YAML in src/content/guides/ and src/content/planks/ can stay on disk doing nothing, or be deleted with it. No data in the old collections was ever written to, so there is nothing to restore and no backfill to undo — the worst case is losing drafted platform copy, which lives in git history regardless.

After cutover (the third PR) rollback is a slightly bigger deal, because that PR redirects /issues/* and repoints the nav. Reverting it restores both, and the guides go back to being unlisted pages. The issues collection is deliberately left in place through that PR rather than deleted, precisely so the revert is a one-commit operation.
