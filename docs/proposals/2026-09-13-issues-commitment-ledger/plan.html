Issues at Two Speeds

The /issues section has to satisfy a reader who gives it twenty seconds on a phone and a reader who wants to check every number. This plan restructures the content model and the page around a single unit — the commitment — so one page and one URL serve both, and locks the shape before more policy content gets written into it.

Grounded against main @ 07970fe — 2026-09-13.

Summary

The six /issues detail pages already contain thirty-six concrete policy commitments, but they're buried three levels deep in "Solution" bullet lists set smaller than the surrounding prose, inside full-bleed color bands that spend most of a phone screen on padding rather than text. Nothing on the pages is sourced, a latent bug drops the background entirely on any issue's fourth sub-section, and a detail page dead-ends at its last bullet with no path to donate, volunteer, or read the next issue. This matters now because the campaign is about to add more policy content, and the current layout doesn't survive that — three times the words makes today's 7-screen Affordability page a 20-screen one.

This plan promotes the commitment to be the first-class unit of the content model, rebuilds the issue detail page as a scannable ledger of commitments with the full problem/mechanism/ sources behind a native disclosure, rebuilds the /issues index as a real table of contents instead of a copy of the homepage grid, and fixes four small pre-existing bugs along the way. It ships as four PRs in two phases — see Phases, PRs, and Spikes — with the schema and structural work landing first so the redesign in phase two only has to be built once, in one shared component, not once per locale.

Approach

Chosen approach: the Commitment Ledger

Restructure each sub-issue's content from a single problem/solution paragraph pair into a list of commitments — first-person, checkable statements ("Require 30% of all new housing built to be affordable housing") that already exist today, just buried in bullet lists. Each commitment renders as one row: the bold statement plus a one-line, always-visible why, with the existing problem prose, the governing mechanism (authority), a rough timeline, and numbered sources behind a native <details> disclosure. An "expand all" control and stat tiles under a one-line stance headline replace the alternating full-bleed color bands, and the /issues index becomes a single table of contents listing every commitment by issue.

This wins over the alternatives below because it's the only shape that serves a twenty-second phone reader and a fact-checking deep-diver from the same page and URL, scales to roughly ten commitments per issue without the page feeling longer (native disclosure is a zero-JS pattern — see the accessibility note under Q1), and needs no new dependency or infrastructure: it's a schema change plus a template rewrite on a static Astro site that already ships zero client-side framework for this section.

Weighed

Alternatives considered

Rejected

Separate summary + details pages

The obvious first idea: a short summary page per issue, linking out to a long details page. Doubles the writing (every commitment gets written twice, in two voices), splits search authority across two URLs per issue, and forces the twenty-second reader to make a "do I want the long version?" decision at exactly the moment they're deciding whether to bounce. A single page with an in-page disclosure gets the same effect without the duplication.

Partially adopted

Field Guide — one commitment per full-bleed band

Keeps today's alternating color bands but gives each one a single giant stat or pull-quote and exactly one commitment, with detail in a side sheet. The strongest first impression of anything considered — each band is basically a shareable image — but length still scales 1:1 with commitment count (ten commitments is ten bands), it needs an ongoing illustration budget per band, and detail living off-page in a sheet is easy to miss and hard to link or print for a deep-diver. Its stat-tile hero is worth keeping; the rest doesn't survive content growth.

Partially adopted

Platform Index as the issue page itself

Make every issue page a filterable table of every commitment across the whole platform, not just that issue. Genuinely the best artifact for an endorsement questionnaire — one linkable, filterable URL for all thirty-six commitments — but cold as a landing experience for someone arriving from a social link with no context yet. Right shape for the /issues index specifically (see PR 4 of 4 below); wrong shape for an individual issue's detail page.

Rejected

Master-detail two-pane layout

A documentation-style layout — a persistent left index of commitments, an expanding right-hand detail pane, no page navigation at all. Common for desktop reference sites, and it would satisfy both readers from one URL too. Rejected because this campaign's actual traffic pattern is a phone reader arriving from an Instagram or text-message link (per the PostHog issue_viewed event already wired up in src/pages/issues/[id].astro) — a fixed two-pane layout has no good mobile translation and would need its own from-scratch responsive treatment, adding real complexity to solve a problem in-page disclosure already solves for free.

Design

Design

See design.html for the full mockup: the issue detail page at rest on a phone, the "today vs. proposed" rendering of one real commitment, the /issues index as a table of contents, and the new page-foot exit block. Every mockup uses the site's actual copy and color tokens (--color-primary etc. from src/styles/global.css) rather than placeholder text, so it can be checked directly against the live site.

One interaction decision worth flagging here: commitments default to fully collapsed with only the bold statement and its "why" line visible — see Q1 for the case against defaulting the first one open instead.

Schema

Schema changes

The issues content collection (src/content.config.ts) gains an optional commitments array on each sub-issue plus issue-level stance, tags, related, stats, and sources fields — every existing field stays and the current problemsAndSolutions shape becomes optional rather than required, so nothing breaks mid-migration. Full detail, including the exact Zod shape and the migration/rollback strategy, is in schema.html.

Build order

Two phases: phase one is invisible prep work that ships no visual change and can land in either order; phase two is the actual redesign, which depends on phase one being done first so it's built once, not per locale.

Open questions & risks

Q1

How much of a commitment's detail should be visible by default?

The design in design.html ships every commitment fully collapsed — bold statement plus one-line "why," nothing else, until tapped. The alternative is defaulting the first commitment per issue open, which proves there's real substance behind the toggle at the cost of a bit more length on first paint.

Recommendation:

Ship fully collapsed with a visible "expand all" control next to the stat tiles. Native <details> plus an always-visible "why" line already tells a skimming reader there's more without opening anything — the accessibility research behind this pattern (WCAG disclosure guidance) treats the collapsed default as the norm precisely because the trigger and its label are what signal depth, not the open state.

Alternative:

First-commitment-open-by-default, if early feedback says the disclosure reads as concealment rather than organization.

Q2

Is the campaign committed to sourcing every statistic before PR 3 of 4 ships?

The whole design leans on citations as the cheapest available credibility upgrade — the stat tiles and footnote markers are load-bearing in the mockup. Partial sourcing (some numbers cited, others bare) reads worse to a hostile reader than sourcing none at all, because it invites the question of why the uncited ones weren't.

Recommendation:

Source every number that appears in a stat tile or gets a footnote marker before PR 3 ships; for any number that can't be sourced in time, cut it from the hero stats and leave it in the collapsed prose unmarked rather than shipping a bare superscript next to sourced ones.

Alternative:

Ship with an explicit "sources being compiled" note on the affected stat tiles if sourcing genuinely can't finish in time — honest about the gap rather than silent about it.

Q3

Do the six per-issue SVG illustrations survive the redesign?

Direction A's ledger has no half-page hero for the illustration to occupy the way today's layout does. They're a real piece of the campaign's visual identity, not filler.

Recommendation:

Move them to the /issues index (PR 4 of 4) as the visual marker for each issue row — they do real work there distinguishing six list items at a glance, and the detail page can stay text-first without losing them from the site.

Alternative:

Keep a smaller version in the stance hero on the detail page if the illustrations are judged too central to the brand to move off that page entirely.

Q4

Should the Spanish site ship in the same PRs as English, or can it lag?

After PR 2 of 4 the two locales share one component, so shipping the ledger to both is structurally free. What isn't free is translation: every new why, authority, and commitment string (up to 108 new strings across 36 commitments) needs a Spanish twin, per the _es-suffix convention already used throughout src/content.config.ts.

Recommendation:

Ship the component and schema to both locales in PR 3/4 of 4, but let Spanish content translation lag behind English by a defined window (e.g. two weeks) rather than blocking the English launch — see F1 below, which tracks this as required follow-up work rather than in-scope for this plan.

Alternative:

Block the whole redesign on having both locales' content ready simultaneously, if a lagging Spanish site is not acceptable to the campaign for equity reasons.

Q5

How rigorously does each commitment's authority need to be verified before publishing?

This surfaced during the investigation, not in the original design: the new authority field states which governmental mechanism enacts a commitment (a zoning text amendment, a budget line, a ballot referral). Getting this wrong — claiming Council can do something it legally can't — is a factual, checkable claim a hostile reader (a rival campaign, a reporter) can and will verify, unlike a stylistic choice.

Recommendation:

Treat authority as optional per-commitment (already true in the schema — see schema.html) and only fill it in once actually confirmed, rather than guessing to fill the field for every row before PR 3 ships. A commitment can go live with just its statement and "why"; authority and timeline can follow once verified.

Alternative:

None seriously worth considering — guessing at legal mechanism to avoid an empty field is strictly worse than leaving it blank.

Follow-ups after this plan ships

Required

F1
What:

Translate every new _es field — why_es, authority_es, commitment_es — across all 36 commitments in all 6 issues.

Why:

Without it the Spanish site either shows blank fields or silently falls back to English mid-sentence, which is worse for a Spanish-speaking reader than the current, fully-translated (if thinner) content.

Why not in the plan:

It's translation labor, not engineering — it depends on PR 3 of 4's English copy existing first, and bundling it into that PR would block a reviewable code change on a content-writing task with its own separate timeline (see Q4).

Optional

F2
What:

Tag-filter chips on the /issues index, plus a print-friendly view for endorsement questionnaires.

Why:

Once the platform crosses roughly fifteen commitments, a flat list of headlines under six issues starts to feel long; filtering by tag (housing, safety, cost-of-living) makes the index scale.

Why not:

At today's 36 commitments across 6 clearly-labeled issues, a flat list is still easy to scan — filtering now would be UI for content that doesn't exist yet.

F3
What:

Replace the parallel /es/ directory tree (separate page files per locale) with a formal Astro [lang] route parameter across the whole site, not just the issues section.

Why:

It would remove the last structural duplication this plan doesn't touch — header, footer, and layout files are still copy-pasted per locale even after PR 2 of 4 unifies the issue page specifically.

Why not:

It's a site-wide routing change touching every page, not just /issues, and the current duplicate-file pattern — while imperfect — is a working convention the rest of the site already relies on; rewriting it is a bigger bet than this proposal's scope justifies for two locales and roughly a dozen page files.

F4
What:

Once PR 3 of 4 has been live for a release cycle with no need to roll back, delete the now-unread problemsAndSolutions field from the schema and from all 6 YAML files.

Why:

Removes a dead, unread field from the content schema, keeping the schema honest about what the templates actually render.

Why not:

Leaving it a little longer costs nothing and keeps a same-PR rollback path — see the Rollback section of schema.html — until the new shape has proven out in production.
