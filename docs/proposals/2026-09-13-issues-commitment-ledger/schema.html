Why nothing here is a new table

Every addition is a field on the existing issues collection, at either the issue level (stance, stats, sources, ...) or nested inside the existing subIssues array (commitments). Astro content collections are file-backed YAML, not a relational database — there's no join or foreign key to design, just a Zod shape that either validates or doesn't at build time. A commitment's sources array holds numeric ids that resolve against the same issue's sources list, not a global registry, because every current statistic in the content is issue-specific and there's no present need for a source to be shared across issues.

Required vs. optional, per new field

FieldRequired?Why
commitment / commitment_esRequiredWithout it there's no row to render — this is the one field a migrated commitment can't omit.
why, authority, timeline, sourcesOptionalPer plan.html Q5 — a commitment can ship with just its statement and grow depth over time as authority/sources get confirmed, rather than blocking on all four being ready at once.
stance, stats, sources (issue-level)OptionalLets PR 1 of 4 migrate one issue without every other issue needing these fields yet.
tags, relatedOptionalNot read by any template until PR 4 of 4; adding them earlier costs nothing and lets content authors fill them in as they migrate each issue.
Rollout

Migration strategy

Backward compatibility

Fully additive — problemsAndSolutions stays valid and commitments is optional, so the schema itself never forces a "both shapes must exist" state. In practice, PR 3 of 4 migrates all 6 issues' content in the same PR that ships the new template, so production never actually renders a mix of old- and new-shape sub-issues; the optionality exists for safety during that PR's own review, not as a long-lived dual rendering path.

Backfill

This is content work, not a script. Each of the 14 existing problemsAndSolutions entries needs its solution bullets split into individual commitments — 36 bullets in total, already counted directly against main. The problem text can carry over largely as-is; commitment and why need new, purpose-written copy for every row, and authority/timeline/ sources need real research per plan.html Q5 and Q2. Budget this as the bulk of PR 3 of 4's actual effort, not as an afterthought to the template work.

Rollback

Because the schema change is additive and Astro content collections are just YAML files under git, reverting PR 3 of 4's commit reverts both the template and the content back to the last known-good state in one step — no separate data migration to undo. This is also the reasoning behind F4: problemsAndSolutions stays in the schema and in git history for one full release after the ledger ships, so a revert has somewhere to land even after content has been rewritten in place.
